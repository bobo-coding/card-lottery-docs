## 0. 四条结论

1. **HOBBY STOCKS 的功能骨架可以整体借用，但两个核心部件必须替换**：
   分队单元从"球队"换成キャラクター枠（03 §3）；开盒从"商家主播自播"换成"平台集中开盒 + 录像"（04 §10 I5）。
   其余 —— 组队拆卡、卡片仓库、单卡查价、评级入口、商城、多商家 —— 与本平台设计同构，**说明 04/05 的方向在真实市场已有对应形态**。
2. **DOPA 只贡献"日本用户看得懂的界面语言"**：场次卡片、残口进度、品类 Tab、全屏演出的手感。
   演出在本平台只能**播放已确定的真实结果**（分位公示、开封高光），不得制造或暗示随机。
3. **HOBBY STOCKS 的公开问题正是本平台要解决的**：商家主播自播开盒（信任落在商家身上）、
   未成年人用成人账户消费 ¥2.76 万且退款无据（06 资本层风险的同型实例）。
   **照抄功能就会照抄这两个问题** —— §1.3 的改造项就是针对它们。
4. **功能量的重心在后台，不在前台**：全部 26 个模块中，用户端 13 个、商家端 4 个、运营端 9 个；
   但 MVP 的 P0 工作量主要在**运营端**（主数据、入库验封、开盒工位、归属、仓储、财务）。
   这是 05 §7"运营密集型生意"在产品拆解上的直接体现 —— **Breaking 平台的产品本质是一套履约操作系统，
   用户 App 只是它的前台。**

### 1.4 HOBBY STOCKS 的两个结构性问题（本平台必须避开）

**问题一：信任落在商家身上。**
商家主播自己采购、自己开、自己播 —— E1 之外的 E2 影像、E3 分队、E4 发货全在商家一方。
用 00 §2.3 的判据：**单方完全控制 → 信任上限 = 该商家声誉**。
这就是本平台 04 §0.1 三方分权要解决的问题，也是**功能上唯一不能借用**的部分。

**问题二：未成年人管控。**
2023-06，一名 15 岁用户用其兄的成人账户、经人脸识别的微信支付，一夜在该平台商家"爱卡球星卡"
购买球星卡盲盒共 **¥27,627.6**（单笔 ¥358.8–¥7,176）。平台回应：消费者证据不足，
"在提供充分证据的前提下"才可退款。

> 这是 06 §2.4（卡游）资本层风险在**拆卡平台**上的同型实例。
> 教训：**实名 ≠ 年龄管控**。账户实名后仍可被他人使用；
> 本平台须在**支付环节**加限额与冷静期（M2），并把相关记录留作可审计证据。
> ⚠️ 单一媒体报道，事实以报道为准，不作为对该平台的定性。

## 3. 产品全景

### 3.1 角色

| 角色 | 身份 | 主要诉求 | 权限边界 |
|---|---|---|---|
| **用户** | 18+ 实名；主力为收藏型、投资型（02 §7、03 §4.4） | 买位、看开盒、拿到卡、确认公正 | 只能操作自己的位与藏品 |
| **公开访客** | 未登录者、媒体、竞品用户 | 独立验证某场次是否公正 | 只读公开开盒记录与验证器 |
| **商家** | 持古物商許可的法人 / 个人事业主（MVP 仅自营） | 上架场次、卖出位、拿到结算 | 定标的、分位、价格、时间；**无权碰随机与录像**（I4 / I5） |
| **自营团队** | 平台内部的商家角色 | 同商家 | 同商家，**且与随机 / 录像系统权限隔离**（04 §7.4 G5） |
| **运营 · 审核** | 平台员工 | 场次合规、主数据准确 | 审核场次、维护主数据 |
| **运营 · 开盒员** | 集中开盒场地员工 | 按排期开盒、录入卡片 | 仅操作工位端；**不能改随机结果** |
| **运营 · 仓管** | 集中仓员工 | 入库验封、寄存、合单、发货 | 仅仓储端 |
| **运营 · 客服 / 仲裁** | 平台员工 | 处理咨询、申诉、仲裁 | 仲裁依据 OpeningRecord，裁定留痕 |
| **运营 · 风控** | 平台员工 | 关联账号、异常消费、未成年人 | 冻结 / 限制账户 |
| **财务** | 平台员工 | 托管、退款、结算、对账、税票 | 资金操作双人复核 |
| **系统** | 平台服务 | 执行不变量、随机、状态机 | 随机与录像只由系统执行 |

**两条新增的流程规则**（由 04 推出，04 未显式写出）：

| 规则 | 理由 |
|---|---|
| **标的入仓验封完成，场次才可开售** | 集中开盒后，04 §5.2"商家逾期未开盒"的风险转化为"商家未交货"；前置入仓把它消灭在开售前 |
| **寄存与商家结算解耦**：以"归属完成 + 入仓"为商家履约完成点，而非用户签收 | 用户可长期寄存；若以签收为结算点，商家回款无限期延后。⚠️ 需律师确认托管结构（04 §7.3） |

### 4.2 用户主流程

```
首次：注册 → 实名 + 年龄验证 → 设置限额（可跳过，默认值生效）→ 玩法教育（"满员才开"）
购位：发现 → 详情（看证据）→ 选位 / 随机 N 位 → 锁定 → 支付 → マイ枠「満員待ち」
等待：满员通知 → 分位公示（RANDOM）/ 顺位公示（DRAFT）→「待開封」→ 日历提醒
开盒：直播（可选）或事后看录像 → DRAFT 选卡会话（仅 DRAFT）→ 结果与归属明细
验证：一键验证（可选）→ 每张卡跳录像时间点
履约：卡进仓库（默认寄存）→ 累积 → 合单发货 → 签收
异常：申诉 → 仲裁 → 裁定通知
```

### 4.3 五种分位类型的差异流程

04 §4.1 的五种分位类型共用主流程，差异集中在**购位交互**与**归属时点**：

| 类型 | 对应玩法 | 购位交互 | 随机 | 归属时点 | 用户额外步骤 |
|---|---|---|---|---|---|
| **ENUMERATED** | キャラ枠（J3，主力） | PICK：挑角色枠（差异价）/ RANDOM：随机分配枠 | RANDOM 时有 | 开盒后识别 | 无 |
| **POSITIONAL** | パック番号（J1）、盒号 | PICK 挑号 / RANDOM 随机号 | RANDOM 时有 | **开盒前已定** | 无 |
| **ATTRIBUTE** | 番号レンジ（J4） | 同上 | RANDOM 时有 | 开盒后规则匹配 | 无 |
| **WHOLE** | BOX 丸ごと（J6） | 单位买断 | 无 | 无需判定 | 无 |
| **DRAFT** | Hit Draft（B8） | 买"参与权" | **顺位随机** | **开盒后交互** | **在线选卡会话**（F6.5） |

> J5 複数BOX混合 是**标的构成**而非分位类型，可与 POSITIONAL / ENUMERATED 组合。
> **DRAFT 是唯一需要用户开盒后在线操作的类型**，缺席即由系统按规则代选（规则上架时声明、写入快照）。
> 这与 04 §6.4"用户缺席不受损"一致，但**"代选规则"本身须事前公开**，否则构成事后裁量。

### 12.1 场次卡片（D3 布局 + H1 内容）

```
┌──────────────────────────────┐
│ [BOX 实拍 · 封条可见]           │
│ ポケカ「XXX」2BOX キャラ枠      │
│ ─────────────────────────── │
│ ¥2,800〜/枠   参考: BOX ¥5,400 │
│ 保底: 各枠 3 パック以上          │  ← 替代 D3「最低保証 ¥xxx」
│ ███████████░░░ 残り 4/20 枠    │  ← D3 残口，语义为"距满员开封"
│ 開封 9/28 20:00  ・ 検証可能 ✓  │  ← 承诺时刻 + 种子已承诺
│ [キャラ枠] [自営] [残りわずか]   │  ← D3 标签体系
└──────────────────────────────┘
```

| DOPA 字段 | 本平台字段 | 语义变化 |
|---|---|---|
| 最低保証（¥ 估值） | 保底（实物张数 / 包数） | 运营估值 → 厂商实物，无需估值权 |
| 残り〇/〇口 | 残り〇/〇枠 | 库存 → 距满员开封 |
| — | 参考零售价 | 让用户算得出溢价 |
| — | 検証可能 ✓ | 点开直达种子 hash |

> ⚠️ **参考零售价会让用户直接算出溢价**（05 §2 透明性悖论）。是否默认显示见 §14 PD2。

### 12.2 场次详情首屏顺序

```
① 标的实拍 + 封条照片
② 保底承诺 + 分位方案（每位定义与价格）
③ 满员进度 + 截止时刻 + "未满员全额退款"
④ 开封时刻 + 种子承诺 hash
⑤ 商家 / 自营标识
⑥ [購入]
```

> 证据在按钮之前 —— 日本用户"要证明不要氛围"（03 §2.2）。

### 12.3 演出规则（D5 手感，用在真实事件上）

| 事件 | 随机来源 | 可做 | 禁止 |
|---|---|---|---|
| **分位公示** | 平台可验证随机（已算完） | 位号翻牌 / 角色枠揭示；结束即显示验证入口 | "差一点"类近失效果 |
| **开封高光** | 厂商密封盒（物理） | SAR 等出现时特效叠加、归属位高亮 | 遮挡卡面；剪辑改变时间顺序 |

**两条硬规则**：
1. **演出是结果的播放器，不是生成器** —— 不得早于或独立于真实结果
2. **演出可跳过，录像不可替代** —— 录像特效层可关闭，审计视图必须是原始画面（I5）

## 13. MVP 切分

**MVP 唯一目标：实测 `m` 与 `k`**（05 §10）。不服务这两个数、且不属于法定 / 信任底线的功能，一律不进 MVP。

| 阶段 | 形态 | 用户端 | 商家端 | 运营端 | 验证目标 |
|---|---|---|---|---|---|
| **MVP** | 自营 + 集中开盒 + 集中仓；**录像先行、不做直播** | M1、M2（F2.1/2.2/2.5）、M3（F3.1–3.5、3.9）、M4（除 F4.8、F4.13）、M5（F5.1–5.4）、M6（F6.1–6.2）、M7（F7.1）、M8（F8.1–8.6）、M9（F9.1–9.4、9.8）、M11（除 F11.5/11.6）、M12 | M15（除 F15.6/15.9）、M16 | M18（F18.1–18.3）、M19（F19.1–19.4）、M20、M21（除 F21.8）、M22（F22.1–22.4）、M23、M24（除 F24.6）、M25（F25.1/25.2/25.6）、M26（F26.1–26.3） | `m`、`k`、满员率、验证点击率、每场工时 |
| **P1** | 加直播、DRAFT、会员、第三方商家 | F4.8、M6 演出与 DRAFT、M7 直播、F8.7/8.8、M10、F11.5 | M14、M17 | F18.4、F19.5、F21.8、F24.6、M25 结算与发票、F26.4/26.5 | 复购率、角色情感假设 |
| **P2** | 规模化 | F7.5、F9.7、M13 | F17.5 | — | — |

> **为什么 MVP 不做直播**：直播不产生 `m`/`k` 证据；且商家直播正是要避开的信任结构（§1.4 问题一）。
>
> **为什么 MVP 就做一键验证（F8.3）与公开站**：它是本平台区别于 DOPA / HOBBY STOCKS 的**唯一用户可感知**界面。
> 不做它，MVP 测到的 `m` 只是"又一家开盒站"的溢价，而不是"可验证开封"的溢价。
>
> **为什么 MVP 就做 M2 消费保护**：§1.4 的案例说明它无法事后补；且它是资本层证据，越早积累越有价值。
