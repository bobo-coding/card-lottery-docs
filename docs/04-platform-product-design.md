# 平台产品设计：多商家 Lottery 开盒平台

> 前置：[01 形态分类](./01-product-taxonomy.md) · [02 市场格局](./02-market-landscape.md) · [03 Breaking 玩法与日本落地](./03-breaking-mechanics-japan.md)
> 本文承接 03 的四条法律硬约束（C1–C4），并将其从"运营策略"升级为**系统不可绕过的强制约束**。

---

## 0. 需求带来的结构性变化

本次定位为**多商家平台**（第三方商家 + 自营），这改变了 03 的核心信任论点：

```
03 的论点：随机性来自厂商密封盒 → 「运营无法决定中身」
本次结构：引入第三方商家 → 商家成为新的作弊面
```

**必须正视**：[02 §5](./02-market-landscape.md) 记录的北美三起信任危机
—— Backyard Breaks 托价刷单、Fanatics 定向分配好盒给关系主播、Whatnot 重封包冒充原封
—— **全部是第三方商家在平台上作弊**，正是本次要建的结构。

**照搬 Whatnot/Fanatics 的市场模式，就会继承它们的全部信任问题。**

### 0.1 解法：三方分权

不是"信任商家"，而是**让任何单方都无法独自操纵**：

| 主体 | 决定什么 | 无权决定 |
|---|---|---|
| **厂商** | 盒内**内容** | 分位、归属 |
| **平台** | **分位随机**、录像采集、归属裁定 | 内容（盒是密封的） |
| **商家** | 上架什么、定价、分位方案、时间 | **内容、随机、录像** |

> **「商家决定不了分位，平台决定不了中身，厂商决定不了归谁」**
>
> 这比单运营方模式**信任更强**：单运营方要自证清白，三方分权是**结构上无法独自作弊**。
> 且串谋必然留痕 —— 随机由平台执行且**先于商家接触标的物**完成承诺。

这是本平台相对 DOPA 与 Whatnot 的**双重差异化**，也是全文设计主线。

## 1. 产品定位

**一句话**：商家上架密封卡盒的众筹开盒场次，用户购位，平台按承诺的随机规则分位、
定时直播开盒、并永久保留可复算的开盒记录。

| 维度 | 定位 |
|---|---|
| 商业模式 | 市场（Marketplace）+ 自营 |
| 收入 | 商家佣金 + 上架/增值服务费 |
| 核心资产 | **可回溯的公正性记录**与商家治理能力 |
| 不做 | 现金回收、积分提现、重封包（见 §3 强制约束） |

## 2. 核心对象模型

### 2.1 场次（Lottery）

平台的核心聚合根。一个场次 = 一次完整的"售位 → 随机 → 开盒 → 归属 → 履约"。

```
Lottery
├─ 基本：id, merchant_id, status, 自营标识
├─ 标的 Subject
│   ├─ items[]：{商品ID, 厂商, 系列, 密封单位(PACK/BOX/CASE), 数量}
│   ├─ 货源凭证：进货凭证、封条状态照片
│   └─ 标的总成本（用于佣金与保底校验）
├─ 分位方案 PartitionScheme      ← 多形式的核心，见 §4
│   ├─ type：ENUMERATED | POSITIONAL | ATTRIBUTE | WHOLE | DRAFT
│   ├─ slots[]：{slot_id, 名称, 定义, 定价, 保底承诺}
│   └─ 归属规则 AttributionRule：{判定时点, 判定方式, 兜底条款}
├─ 售卖方案 SaleScheme
│   ├─ 售卖窗口 [开始, 截止]
│   ├─ 总位数, 成团阈值（强制 = 100%）
│   ├─ 定价模式：UNIFORM | DIFFERENTIATED
│   ├─ 选位模式：PICK（用户挑）| RANDOM（随机分配）
│   └─ 限购规则（单用户上限）
├─ 开盒方案 OpeningScheme
│   ├─ 计划开盒时刻（承诺，逾期须公示）
│   ├─ 直播频道
│   └─ 录像规格（强制，平台采集）
├─ 公正性 FairnessSpec           ← 见 §6
│   ├─ server_seed_hash（上架即公示）
│   ├─ 熵源：PARTICIPANTS | PUBLIC_BEACON
│   └─ 算法版本
└─ 保证 Guarantees
    ├─ 每位最低张数（强制 > 0）
    └─ 退款政策（流拍/逾期/异常）
```

### 2.2 位（Slot）与持位（Holding）

```
Slot：场次内的分位单元      {slot_id, 定义, 定价, 保底承诺, 状态}
Holding：用户对位的持有关系  {user_id, slot_id, 购买价, 购买时间, 支付单号}
```

**Slot 状态**：`可售 → 锁定中(待支付) → 已售 → 已分配用户 → 已归属 → 已履约`

> 「锁定中」有超时释放，防止占位不付款卡住成团。

### 2.3 开盒记录（OpeningRecord）

**平台的核心资产**，永久不可变，见 §6。

## 3. 强制约束层：先于配置

**这是本设计最重要的架构决策：约束层在配置层之上，商家配置不出违规场次。**

03 §6.2 的四条硬约束在市场模式下不能靠运营审核，必须是**系统不变量**：

| # | 不变量 | 来源 | 校验时点 |
|---|---|---|---|
| **I1** | 每位最低张数 > 0，且分位方案必须穷尽标的 | L3 每位保底实物 | 上架校验 |
| **I2** | 成团阈值 = 100%，**商家与平台不得自持位** | L2 售罄才开拆 | 上架校验 + 购位拦截 |
| **I3** | 不提供任何现金回收 / 可提现余额 | L1 无现金还流 | 系统无此能力 |
| **I4** | 随机**由平台执行**，商家无权触发、重跑、指定结果 | L4 可验证随机 | 权限模型 |
| **I5** | 录像**由平台采集**，商家不得上传或替换 | L4 全程录像 | 采集链路 |
| **I6** | 种子承诺**先于售位开始**发布 | L4 | 状态机前置条件 |
| **I7** | 禁止重封包（Repack）类标的 | 03 §3.2 | 标的类目限制 |
| **I8** | 商家关联账号不得购买自家场次的位 | 防托价（02 §5） | 购位拦截 |
| **I9** | **禁止按稀有度分位**（如"本盒全部 SAR"独立成位） | 03 §3.2 排除 J2 | 分位方案校验 |

> **I2 + I8 合起来封死"托价 + 自持位"**，这正是 Backyard Breaks 事件的作弊路径。
> **I4 + I5 是三方分权的技术落点** —— 商家碰不到随机和录像，就无法独自作弊。

**违反上述任一条的场次配置，系统直接拒绝创建，不进入人工审核队列。**

## 4. 分位方案体系（"灵活配置多形式"的实现）

### 4.1 五种分位类型

多形式的本质是**分位方案可插拔**，其余（售卖、开盒、归属、履约）共用。

| type | 说明 | 对应玩法 | 归属判定 |
|---|---|---|---|
| **ENUMERATED** | 按枚举清单分位 | 角色枠、球队(PYT/RT) | **开盒后判定**（需识别） |
| **POSITIONAL** | 按位置/序号分位 | パック番号、盒号 | **开盒前已定**（自动） |
| **ATTRIBUTE** | 按卡属性分位 | 卡号段（**稀有度枠禁用**，见下） | **开盒后判定**（规则匹配） |
| **WHOLE** | 单一位，全部归一人 | Personal Break | 无需判定 |
| **DRAFT** | 按顺位轮流挑选 | Hit Draft | **开盒后交互** |

### 4.2 归属判定时点：被低估的关键维度

这是**运营成本与纠纷风险的主要来源**，配置时必须显式选择：

| 判定时点 | 特征 | 成本 | 纠纷风险 |
|---|---|---|---|
| **开盒前已定**（POSITIONAL） | 位与内容的映射先于开盒确定 | **极低**，全自动 | **极低** |
| **开盒后规则匹配**（ATTRIBUTE） | 按稀有度/卡号自动匹配 | 低 | 低（边界卡需仲裁） |
| **开盒后需识别**（ENUMERATED） | 需判断"这张卡属于哪个角色枠" | **高**，人工或识别模型 | **高** |
| **开盒后需交互**（DRAFT） | 需用户在线挑选，有超时 | 中，需 draft 会话 | 中 |

> **ENUMERATED（角色枠）是 03 §3 推荐的主力玩法，但它的归属判定成本最高。**
> 必须在上架时要求商家**预先提交分位清单**（本弹每个角色枠包含哪些卡号），
> 系统据此自动匹配，**把人工判定前移到上架，而不是留在开盒后。**
> 这是角色枠能否规模化的关键 —— 也解释了 03 §3.1 说的"逐弹策划是壁垒"。

### 4.3 分位方案校验（上架时）

```
校验 1：穷尽性 —— 所有可能开出的卡都能映射到某个位（无"孤儿卡"）
校验 2：互斥性 —— 不存在一张卡同时属于两个位
校验 3：保底性 —— 每个位的最低张数 > 0（I1）
校验 4：兜底条款 —— 必须声明未预期卡（错版/加赠）的归属规则
校验 5：非稀有度分位 —— 分位依据不得为稀有度等级（I9）
```

> **校验 5（禁稀有度分位）的理由**：按稀有度分位会造出"SAR 位必赚、RR 位必亏"的确定性结构，
> 直接命中 [03 §6.1](./03-breaking-mechanics-japan.md) ③"部分参加者纯亏"这一赌博风险点。
> 卡号段（ATTRIBUTE 的合规用法）不同 —— 号段与价值无必然对应，不构成确定性亏损位。

> **校验 4 常被忽略但必然发生**：厂商偶尔放入清单外的卡。
> 无兜底条款 → 开盒后无法归属 → 纠纷。**强制商家上架时声明。**

### 4.4 选位模式 × 分位类型

| | PICK（用户挑） | RANDOM（随机分配） |
|---|---|---|
| **是否需要平台随机** | 否 | **是**（走 §6 流程） |
| 定价 | 通常 DIFFERENTIATED | 通常 UNIFORM |
| 对应 | PYT、Pick Your Slot、角色枠挑选 | RT、Random Slot |

> PICK 模式不需要随机，但**仍需完整开盒记录**（录像 + 归属明细）。
> 公正性体系覆盖两种模式，只是随机环节可空。

## 5. 场次生命周期与状态机

```
草稿 DRAFT
  │ 提交（触发 §3 不变量校验 + §4.3 分位校验）
  ▼
待审核 PENDING_REVIEW ──拒绝──▶ 已拒绝 REJECTED
  │ 通过（平台生成种子并公示 hash —— I6）
  ▼
售位中 ON_SALE
  │                    ╲ 截止未满
  │ 售罄(100%)          ╲
  ▼                      ▼
已锁定 LOCKED          流拍 FAILED ──▶ 退款完成 REFUNDED
  │ 平台执行随机（I4），公示分位结果
  ▼
待开盒 READY
  │ 到达计划时刻，平台开启采集（I5），直播开始
  ▼
开盒中 OPENING
  │ 开盒完成
  ▼
归属中 ATTRIBUTING
  │ 按 AttributionRule 判定（自动/人工/draft 交互）
  ▼
归属完成 ATTRIBUTED
  │ 生成 OpeningRecord，永久归档
  ▼
履约中 FULFILLING ──▶ 已完成 COMPLETED
```

### 5.1 关键时序（不可调换）

```
种子承诺 ──▶ 售位开始 ──▶ 售罄截止 ──▶ 执行随机 ──▶ 分位公示 ──▶ 开盒
   I6            必须在承诺之后        必须在参与者确定后   必须先于开盒
```

**为什么这个顺序不可变**：
- 种子先于售位 → 平台无法根据参与者构造种子
- 随机后于截止 → 参与者列表已固定，无法追加/剔除
- 分位公示先于开盒 → 谁拿哪个位在内容未知时已确定，**商家无法针对性调整**

### 5.2 异常分支

| 异常 | 处理 |
|---|---|
| 售位期截止未满 | 流拍，全额退款（I2 不允许降低阈值成团） |
| 商家逾期未开盒 | 宽限期后自动流拍退款；计入商家违约 |
| 开盒中录像中断 | **场次中止**，全额退款；录像完整性不可妥协 |
| 出现清单外卡 | 按 §4.3 校验 4 声明的兜底条款 |
| 归属存在争议 | 冻结履约，人工仲裁，依据 OpeningRecord |
| 商家履约失败 | 保证金赔付，见 §7.3 |

## 6. 公正性与可回溯体系

**平台的核心资产。设计目标：任何第三方可独立复算，无需信任平台。**

### 6.1 可验证随机

```
① 上架时：平台生成 server_seed，公示 SHA-256(server_seed)      ← 承诺
② 售位截止：参与者列表固定，生成 participants_hash
③ 熵源合成：final_seed = H(server_seed ‖ participants_hash ‖ beacon)
④ 执行分配：assignment = Shuffle(slots, final_seed, algo_version)
⑤ 公示：揭示 server_seed，公布全部输入与输出
```

**熵源选项**：

| 熵源 | 强度 | 说明 |
|---|---|---|
| PARTICIPANTS | 中 | 参与者列表哈希；平台仍可试算种子（需在承诺前，成本高） |
| **PUBLIC_BEACON** | **高** | 引入**开盒后才产生**的公开不可预测值（如指定时刻的公链区块哈希） |

> **建议默认 PUBLIC_BEACON**：种子承诺在前、公开信标在后，
> **平台即使想操纵也无法预知信标值** —— 这是"无需信任平台"的唯一强形式。
> 代价是须依赖外部信标可用性，需设降级方案（信标缺失 → 顺延或退款，不得静默回退）。

### 6.2 开盒记录结构

```
OpeningRecord（永久不可变，公开可查）
├─ 场次快照     上架时固化的分位方案、定价、保底承诺（防事后篡改）
├─ 种子承诺     hash、承诺时间戳、公示位置
├─ 参与者       位号 → 用户(脱敏ID)、购买时间
├─ 随机执行     种子揭示、熵源取值、算法版本、输入输出、**可复算脚本**
├─ 分位结果     位号 → 用户
├─ 开盒影像     连续录像、封条特写时间点、分段校验和
├─ 归属明细     每张卡 → 位号、判定方式(自动/人工)、判定人、**对应录像时间点**
└─ 履约         运单号、签收状态
```

### 6.3 三条设计要求

1. **可独立复算**：公开算法与输入，提供验证脚本，用户自行运行得到相同结果
2. **影像与归属互相锚定**：每张卡的归属记录指向录像时间点，可跳转核对
3. **快照防篡改**：分位方案与保底承诺在上架时固化，商家事后无法修改

### 6.4 录像的定位（承接 03 §5）

本次需求确定要**直播**开盒。与 03 §5 建议的"录像优先"整合如下：

| 层 | 作用 | 业务依赖 |
|---|---|---|
| **直播层** | 体验与社群，实时观看 | **不作为收入前提** |
| **录像层** | **审计凭证**，永久可查、可复算 | **信任的唯一来源** |

> **关键**：开盒**按计划时刻执行，不因观看人数而改变**；
> 用户**不在场也不受损** —— 分位在开盒前已公示，录像事后可查。
>
> 这样既满足直播需求，又不让商业模式压在
> [02 §3](./02-market-landscape.md)「日本仅 5.8% 买过直播商品」这个薄弱基础上。
> **直播是增益，录像是底座。**

## 7. 商家侧

### 7.1 入驻与资质

| 项 | 要求 | 依据 |
|---|---|---|
| **古物商許可** | **强制**，验真 | 中古卡经手法定要求；DOPA、Minitz 均已取得 |
| 实名与法人信息 | 强制公示于场次页 | 特商法表示义务 |
| 面谈审核 | 建议（Minitz 采用） | 降低欺诈 |
| 保证金 | 强制，与场次规模挂钩 | 履约与赔付 |

### 7.2 商家权限边界（三方分权的落点）

| 商家**可以** | 商家**不可以** |
|---|---|
| 选择标的、定价、设计分位方案 | ❌ 触发/重跑/干预随机（I4） |
| 设定售卖窗口与开盒时刻 | ❌ 上传或替换录像（I5） |
| 上架前修改配置 | ❌ 上架后修改分位与保底（§6.3） |
| 查看自家场次数据 | ❌ 购买自家场次的位（I8） |
| 申请提前结算 | ❌ 降低成团阈值（I2） |

### 7.3 结算与赔付

```
用户支付 ──▶ 平台托管（Escrow）──▶ 履约确认 ──▶ 结算商家（扣佣金）
                    │
                    └─ 流拍/中止 ──▶ 全额退款
```

- **托管至履约确认后放款**，不预付
- 履约失败 → 保证金赔付 → 不足部分计入商家欠款并停业
- 建立**商家分级**：履约率、纠纷率、逾期率 → 影响费率、曝光、保证金比例

> ⚠️ 资金托管可能触及日本**資金決済法**（前払式支払手段/资金移动业），
> **须律师确认托管结构**，见 §10。

### 7.4 自营与第三方的利益冲突治理

平台自营即是商家，构成 **02 §5 中 Fanatics 被指控的同型风险**（定向分配好盒）。

**强制治理措施**：

| # | 措施 |
|---|---|
| G1 | 自营场次走**完全相同**的随机与录像路径，无任何例外通道 |
| G2 | 场次页**显著标识"自营"** |
| G3 | 货源分配（哪些盒给自营、哪些给第三方）**全程留痕可审计** |
| G4 | **定期公开**自营与第三方的中奖分布对比统计 |
| G5 | 自营团队与随机/录像系统**权限隔离**，不得有运维后门 |

> G4 是最强的公信力手段：**用可公开验证的统计，主动证明自营没有优势。**
> 竞品无法轻易跟进 —— 因为它们的分位随机不是平台强制统一执行的。

## 8. 履约

### 8.1 两种模式

| 模式 | 商家直发 | 平台集中仓 |
|---|---|---|
| 平台成本 | 低 | **高** |
| 跨场次合单 | ❌ 不可能 | ✅ |
| 品控与纠纷 | 商家负责，风险高 | 平台可控 |
| 寄存/金库 | ❌ | ✅ 可扩展 |
| 合单系数 k | **恒为 1** | **4+** |

> ⚠️ **本节初稿建议"MVP 用商家直发"，已被 [05 §6](./05-unit-economics.md) 推翻。**
>
> 按 05 的测算，逐位发货（k=1）时履约成本占位售价约三分之一，
> **需 +41% 溢价才保本**；合单（k=4）后降至 **+7.5%**。
> 而**商家直发在结构上无法合单** —— 不同商家、不同场次各自发货。
>
> **修正建议：MVP 即采用平台集中仓。**
> 这与 §10 关于 I5（录像须平台采集）推荐"MVP 用集中开盒场地"的结论一致 ——
> **两条独立推理（经济、信任）指向同一结论：集中化是 MVP 前提，不是规模化后的选项。**

### 8.2 履约时效

商家须在归属完成后 N 日内发货（建议 3 个工作日，对齐日本トレカセンター的"原则24小时内发送"竞争基准）。逾期计入违约。

## 9. 用户侧关键体验

| 场景 | 设计要点 |
|---|---|
| 场次浏览 | 显示分位方案、**每位保底承诺**、已售位数、开盒时刻、商家资质与分级 |
| 购位 | 明确展示"本位可能获得什么"与保底下限；PICK 模式实时位状态 |
| 等待开盒 | **分位结果在开盒前公示**，用户提前知道自己的位 |
| 观看开盒 | 直播可选；**缺席不影响权益** |
| 查看结果 | 归属明细 + **可跳转到对应录像时间点** |
| 验证公正 | 一键查看开盒记录，提供**复算脚本与说明** |
| 履约 | 物流追踪；异常申诉入口指向 OpeningRecord |

> **「分位结果开盒前公示」是信任体验的关键**：用户在内容未知时就知道自己的位，
> 事后无法怀疑"平台按我的身份调整了分配"。

## 10. 未决问题与 Blocker

| # | 问题 | 性质 |
|---|---|---|
| 1 | **众筹法律形态**：权利贩卖型 vs 共同购入代行型（03 §6.3） | **律师判定**，影响资金流与状态机 |
| 2 | **资金托管结构**是否触及資金決済法 | **律师判定**（§7.3） |
| 3 | 平台自营与第三方商家的**竞争关系是否劝退优质商家** | 商务，需早期验证 |
| 4 | 角色枠**分位清单的标准化程度**（能否跨商家复用官方清单） | 决定 ENUMERATED 能否规模化 |
| 5 | 公开信标的**可用性与降级方案** | 技术，影响 §6.1 强度 |
| 6 | 直播采集的**技术方案**（平台采集如何落地到商家现场） | I5 的实现难点，见下 |

### ⚠️ I5 的实现难点

"录像由平台采集，商家不得上传替换"在**商家自有场地开盒**时难以强制
—— 商家用自己的设备、自己的网络。可选路径：

| 方案 | 强度 | 成本 |
|---|---|---|
| 平台指定 App 采集 + 端到端签名 + 实时上传 | 中 | 低 |
| 平台提供标准化采集硬件 | 高 | 中 |
| **集中开盒场地**（商家寄存标的，平台统一开盒） | **最高** | **高** |

> 这是**三方分权能否真正成立的关键落点**。
> 若 I5 无法强制，"商家碰不到录像"就只是承诺而非结构 —— **整个信任叙事会退化到 Whatnot 的水平**。
> 建议 MVP 阶段用**集中开盒场地 + 自营为主**，验证模式后再开放第三方商家自主开盒。
